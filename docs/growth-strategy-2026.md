## 2. ターゲットインサイト

### 真の Job to be done

「オナニーのおかず探し」は表層ニーズに過ぎず、それだけならFANZA直で済むため第三者サイトを経由する理由にならない。

**真のJTBD: 「外したくない・効率よく自分に刺さるやつを見つけたい」キュレーション需要**

| 階層 | ニーズ |
|------|--------|
| 表層 | おかず探し |
| 機能 | ジャンル軸での網羅探索 / 似た系統の横展開 / プロフィール確認 |
| 情緒 | ファンとしての知識欲・推し活 / 読み物として楽しむ |

### 「ハズレ引きたくない」需要は確実に存在

- **パッケージ詐欺・サンプル詐欺**は10年以上議論され続け、アンサイクロペディアやpixiv百科事典に項目化されているレベル。集団的怒りとして共通言語化されている。
- FANZA読み放題の口コミ「玉石混交すぎて『これ！』っていうのが中々見つからなくて使いづらい」
- レビューは点数より内容、自分と好みが似ているレビュアーを見つけることが重要視される
- AV女優の約半数が半年以内に引退 → 常に開拓ニーズあり
- 似た女優検索ツールを個人がAI/Facenetで自作するレベルでニーズ顕在化
- ステマ規制（2023年10月）以降、公式レビューも疑われる流れ

## 3. 競合分析

### 直接競合（AV領域）

| サービス | 強み | 弱み |
|---------|------|------|
| AV女優Wiki系（Seesaa） | 網羅性◎ | レコメンドなし |
| Xcity | 名鑑として権威 | レビュー・レコメンドなし |
| FANZA / MGS | データ完全 | レビュー信頼性低、ジャンル粒度粗 |
| 顔類似AI系（スケベ博士・LINE Bot等） | バズる | 継続性に難・レコメンドが「顔だけ」で浅い |
| 個人レビューブログ・5ch | 生の声 | 散在・非構造 |

**→「レビュー＋抜けるシグナル＋構造化データ」を統合したレコメンドは空白地帯**

### 隣接ジャンルの参考（最重要）

| サービス | 学べる設計 |
|---------|-----------|
| **Filmarks** | 「似ている作品」を**複数次元**（テーマ/レビュー類似/キャスト/舞台）で束ねる |
| **Letterboxd** | トーン類似 + ソーシャル発見性。「好みが似ているレビュアーを見つける」需要に最も応える |
| **MyAnimeList / AniList** | Matrix Factorization、低評価をネガティブシグナルとして学習 |
| **VNDB** | 細粒度タグで勝負（思想が近い） |
| **Spotify** | 行動データ + コンテンツ特徴のハイブリッド |
| **Pixiv** | 成人OKでレコメンドが成立する希少な参考事例 |

## 5. 5つの差別化打ち手

①〜④ は Layer 2 が機能していることが前提。Phase 0-1 で Layer 2 還流の土台を作り、Phase 2 以降で実装する。
⑤ は Layer 1 拡張（顔ベクトル / 特徴タグ）が主軸で、Layer 2 は精度向上の補助に使う。

### ① 博士スコア（作品単位）
- 編集レビュー + クリック密度 + 滞在時間の合成スコア
- 「信頼できるレビュアー需要」に直撃
- Layer 2+3 の合成

### ② 似ている女優の多軸化（**女優ページ上**のレコメンド）
- 現状はコサイン類似度のみ（タグベース）
- 「**作風 × ジャンル傾向 × ファン重複 × デビュー時期**」のブレンドへ
- ファン重複データは Layer 2 が必要

### ③ ホットネス（動的人気度）
- GA4クリックを集約 → 女優・作品ページに「いま抜かれている」シグナルを表示
- 「いま熱い女優Top10」のような動的記事の自動生成も可能
- Layer 2 直

### ④ ローカルストレージお気に入り
- ログイン不要のままCFの種を作る
- LINE Login導入時にサーバへ同期
- Layer 2 を別経路で補強（クリックより強いシグナル）

### ⑤ 画像／特徴から探す検索体験（**入口段階**の探索強化）
**目的**: 「外したくない・自分に刺さるやつを見つけたい」JTBDの**入口段階**を強化する。②が女優ページ上のリコメンドなのに対し、⑤はサイトに来た瞬間の探索フローを変える。

#### ⑤-A. 画像から探す
- 有名人や好きな女優の写真をアップロード → 似ている女優を返す
- 例: 「橋本環奈っぽい顔の女優は？」「この女優に似てる人もう一人いない？」
- 技術: 顔特徴抽出（DeepFace / FaceNet / ArcFace 等）+ ベクトル類似度検索
- 必要データ: 全女優の顔ベクトル化（プロフィール画像から事前計算）
- 競合: 顔類似AI系（スケベ博士・LINE Bot等）はあるが「顔だけで終わる」浅さが弱点。**博士サイトはここに ②似ている女優の多軸化 + ④お気に入り を組み合わせて深さで勝つ**

#### ⑤-B. 特徴から探す
- 体型・顔タイプ・年齢等の属性ファセット検索
- 例: 「童顔 × 巨乳 × 20代前半」「クール系 × スレンダー」
- 必要データ:
  - 体型系（バスト・身長・カップ等）→ FANZA APIから取得可能
  - 顔タイプ（童顔・お姉さん系・クール系・ギャル系 等）→ **独自タグ付けが必要**（AI分類 + 編集校正のハイブリッドが現実解）
- 設計: ジャンルページの仕組みをそのまま転用可能。特徴タグも slug 化して `/face-doukan/` のようなURL構造で SEO 流入も狙える

**→ ②③④⑤ は既存競合に無い差別化で、時間とともにデータが堀になる**

## 7. 制約事項

### FANZAアフィリエイトのサブID制約

公式仕様確認の結果、**FANZAアフィリエイトには「任意文字列のサブID」機能は存在しない**。

#### 公式仕様の事実（DMMヘルプセンター一次情報で確認済み）
- `af_id` は **`基本ID-001`〜`-999`** の3桁数字固定。任意文字列不可
- `001` は最初のサイト登録時に自動発行
- `-002` 以降は **「サイト追加申請」+ 審査** が必要（1サイト=1ID原則）
- レポートは「報酬別 / サービス別 / 商品別」のみ。**「URL別」「ページ別」レポートは公式機能に存在しない**
- 報酬API（成果取得API）は非公開
- `ch` / `ch_id` はリンク生成元識別用パラメータで、ユーザーが書き換えてもレポートに出る保証なし

#### 採用した代替策
**GA4 `fanza_click` イベントのページパス次元集計**で代理計測。売上/件数は分離不可だが、サイト全体CVRをかけて推定可能。

#### 一次情報URL
- アフィリエイトIDについて: https://support.dmm.com/affiliate/article/44084
- 複数サイト掲載: https://support.dmm.com/affiliate/article/44092
- レポートの見方: https://support.dmm.com/affiliate/article/44117
- API IDの取得方法: https://support.dmm.com/affiliate/article/47546

## 8. Phase 2 詳細：お気に入り機能の設計

レコメンドアルゴリズムを将来「協調フィルタリング → Matrix Factorization → コンテンツ特徴ハイブリッド」と進化させる前提で、**最初から (user, item, action, context) のフルセット**を取る。

### 8.1 localStorage スキーマ

```js
localStorage["av-hakase:user"] = {
  v: 1,                                   // schema version
  visitor_id: "uuid-xxxx",                // 永続匿名ID（LINEブリッジの要）
  first_visit_at: "2026-04-30T...",
  favorites: {
    actresses: [
      { slug: "kiyono-saki", added_at: "2026-04-30T...", source: "actress_header" }
    ],
    works: [
      { cid: "1mgold00045", added_at: "2026-04-30T...", source: "work_card_v2" }
    ]
  }
  // 将来追加候補: tags_followed, line_linked, privacy_consent
}
```

`added_at` `source` も保存しておくことで、後から「直近1週間に追加された推し」「どの導線から登録されたか」の分析が可能。

### 8.2 GA4 イベント設計

#### `favorite_add` — 強い正のシグナル

| パラメータ | 型 | 必須 | レコメンドでの用途 |
|-----------|-----|------|------------------|
| `visitor_id` | UUID v4 | ✅ | 永続ID。LINEブリッジ |
| `item_type` | "actress" \| "work" | ✅ | 学習時のテーブル分け |
| `item_id` | string | ✅ | 女優slug / 作品cid |
| `item_name` | string | ✅ | DBジョインなしで分析可能にする保険 |
| `source_page_path` | string | ✅ | コンテキスト |
| `source_component` | enum | ✅ | `actress_header` / `work_card_v2` / `related_actress` etc. |
| `list_position` | int? | △ | ポジションバイアス補正 |
| `referrer_item_id` | string? | △ | 共起シグナル |
| `user_total_favorites_after` | int | ✅ | ヘビーユーザー判定 |
| `user_first_favorite` | bool | ✅ | オンボーディング分析 |
| `ms_since_page_load` | int | △ | エンゲージメント強さ |

#### `favorite_remove` — 強い負のシグナル

| パラメータ | 型 | 用途 |
|-----------|-----|------|
| `visitor_id` | string | ✅ |
| `item_type`, `item_id` | | ✅ |
| `seconds_since_add` | int | 5分未満なら誤クリック扱い（学習除外） |
| `user_total_favorites_after` | int | ✅ |

#### `favorite_item_click` — お気に入り一覧から実際にアクション

| パラメータ | 型 | 用途 |
|-----------|-----|------|
| `visitor_id`, `item_type`, `item_id` | | ✅ |
| `list_position` | int | お気に入り内の何番目を選んだか |
| `destination` | "internal" \| "fanza" | 内部回遊 or 購買行動 |

#### `favorite_list_view` — お気に入りページに来た
- パラメ最小限。ファネル分析用。

### 8.3 visitor_id 設計

GA4 標準の `user_pseudo_id` は不十分（キャッシュクリアでリセット、LINEブリッジ不可）。**自前の `visitor_id` を localStorage に発行・保管**して全イベントに付与する。

```
[初回訪問]
  visitor_id = uuidv4()
  localStorage["av-hakase:user"].visitor_id = visitor_id
  GA4 user property に set_user_properties

[2回目以降]
  visitor_id を localStorage から読み出して全イベントに同梱

[Phase 3でLINE Login時]
  account_link イベント発火: { visitor_id, line_user_id }
  → サーバーで visitor_id ↔ line_user_id を bridge
  → 過去の匿名行動ログをLINEユーザーに紐付け
```

### 8.4 既存 `fanza_click` の再活用

既存イベントにも `visitor_id` を付与することで、**implicit signal** として併用可能。お気に入り0件のユーザーへのコールドスタート対策になる。

| シグナル | 強度 | 取得元 |
|---------|------|--------|
| `favorite_add` | 強 (+1.0) | 新規 |
| `favorite_remove` | 強 (-1.0) | 新規 |
| `favorite_item_click` (FANZA) | 中 (+0.7) | 新規 |
| `fanza_click` | 中 (+0.5) | **既存。`visitor_id` 付与だけ追加** |
| `actress_page_view`+滞在30秒以上 | 弱 (+0.1) | 新規 |
| 単純PV | 極弱 (+0.01) | GA4標準 |

### 8.5 レコメンドモデルへのマッピング

```
協調フィルタリング初期版（Phase 2 で実装）:
  weight = +1.0  (favorite_add)
         × 1.5  if user_first_favorite=false（活発ユーザー重み増）
         -1.0  (favorite_remove, seconds_since_add > 300)
          0   (favorite_remove, seconds_since_add ≤ 300 → 誤クリック扱い)
         + 0.3 (favorite_item_click, destination=internal)
         + 0.7 (favorite_item_click, destination=fanza)

ポジションバイアス補正:
  list_position が高い項目はクリックされやすい → 学習時に重み下げ
```

## 9. 重要な観測事実（GA4過去30日 / 2026-03-31〜04-29）

### サイト規模感

| 指標 | 値 |
|------|-----|
| UU | 9,103 |
| PV | 14,928 |
| セッション | 10,253 |
| エンゲージメント率 | 59.3% |
| `fanza_click` イベント | 1,596 / ユニーク 936人 |
| UU→fanza_click 到達率 | 約10.3% |

### 流入チャネル（Organic 一本足）

| チャネル | 比率 |
|---------|------|
| Organic Search | **89.9%** |
| Direct | 6.7% |
| Referral | 2.0% |
| その他 | 0.5% |

→ 被リンク・SNS はほぼ機能していない。Phase 1 で被リンク獲得をやり切る方針は妥当。

### 太い構造のミスマッチ

- **PV Top10 の9割が「ジャンル別おすすめ記事」**（女優個別ページは1件のみ）
- **fanza_click Top20 は100%「個別女優ページ」**（記事ページは圏外）

つまり「**記事で集客しているが、記事自体はクリックを生まず、女優ページに飛んだ人だけ買っている**」構造。
Phase 1 で「記事 → 女優ページの動線」改善が最重要課題。

### 単一女優依存リスク
- `kiyono-saki` 単体で `fanza_click` 160 = 全体の10%
- 同じ構造の「太い女優ページ」を量産することがCV源拡張の鍵
