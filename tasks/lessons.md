# Lessons Learned

## 2026-03-24: デプロイ前に必ずコミットする

**問題**: 複数の機能実装（記事パーツ拡張）を行った後、コミットせずにデプロイした。外部プロセス（linter等）でファイルが巻き戻された際に作業が失われるリスクがあった。

**ルール**:
- 機能実装が一段落したら、デプロイ前に必ずコミットする
- 特にCSS・PHPの変更は外部ツールで上書きされるリスクがあるため、こまめにコミット
- デプロイスクリプトの先頭で未コミット変更がないかチェックする仕組みを検討

**対策**:
- ルートに `.gitignore` を追加（機密ファイル・ビルド成果物を除外）
- `secret.md`, `*.zip` 等をトラッキング対象外に

## 2026-03-24: バッチ実行順序の厳守（作品画像が女優画像に混入）

**問題**: `fetch_fanza.php` が `actresses.thumbnail_url` を作品のパッケージ画像から設定していた。女優ポートレート画像を取得する仕組みがなく、全女優のサムネイルがDVDジャケットになっていた。

**ルール**:
- バッチは必ず `run_all.php` 経由で実行する（登録→プロフィール→作品の順序を保証）
- `fetch_fanza.php` に女優サムネイル設定ロジックを入れない（プロフィールバッチの責務）
- 個別バッチを単体実行する提案をしない

**対策**:
- `fetch_actress_profiles.php` を新規作成（FANZA ActressSearch API で女優画像を取得）
- `run_all.php` を新規作成（実行順序を保証）
- `fetch_fanza.php` から女優サムネイル設定ロジックを削除

## 2026-03-24: CSS変更は本番確認を必ず行う

**問題**: コミット 51ad22f で genre-card の padding/arrow位置、work-card の画像サイズ/CTAスタイルを変更したが、本番で矢印がジャンルテキストと被り、ジャンルページの表示が崩れた。

**ルール**:
- CSSの変更は必ず本番環境で目視確認する
- 複数コンポーネントのCSS変更を1コミットにまとめない（問題の切り分けが困難になる）
- 既存ページに影響するCSS変更は、変更前後のスクリーンショットで比較する

## 2026-04-01: 記事の@actressスラグは本番DBで必ず検証する

**問題**: 3月デビュー記事で3件のスラグ不一致が発生。(1) `@actress[shiori]`が別の女優(依本しおり)を指していた、(2) 小宮涼歌・山石麻衣香が本番DBに未登録/スラグ不一致でアルファベット表示+404になっていた。

**根本原因**:
- スラグ生成(`register_actresses.php`)が漢字を変換できず、「真宮しおり」→「shiori」（姓が脱落）のように壊れたスラグを生成していた
- `newcomers_kanji_fix.json`にスラグ修正データはあったが、適用するバッチが存在しなかった
- ローカルDBと本番DBのスラグが異なる状態で記事を作成した

**ルール**:
- 記事で`@actress[slug]`を使う前に、必ず本番DBでスラグの存在と正しい女優への紐付けをSSHで確認する
- 漢字名の女優をJSON登録する際は読み仮名を必ず付与する
- `fix_actress_slugs.php`を使ってスラグの事後修正と未登録女優の追加ができる

**対策**:
- `register_actresses.php`: 漢字を含む名前は読みなしでスラグ生成不可に変更、スラグ重複時に警告ログ出力
- `fix_actress_slugs.php`: 新規作成（スラグ修正+未登録女優の登録バッチ）
- `create-debut-article`スキル: Step 2.5に本番スラグ検証ステップを追加

## 2026-05-08: 重い画像への preload / fetchpriority="high" は逆効果

**問題**: TOP モバイル LCP 改善のため、FC2 ランキング 1 位サムネに `<link rel="preload" as="image" fetchpriority="high">` を追加し、rank 1-3 の `<img>` を `loading="eager" + fetchpriority="high"` にした。結果、Performance スコアは **71 → 57** に悪化、LCP は **4.2s → 11.1s** に悪化（2回測定で再現）。即 revert。

**根本原因**:
- preload 対象の FC2 PNG が **約 580KB** と巨大だった
- `fetchpriority="high"` は限られたモバイル帯域でこの巨大 PNG にダウンロード優先権を与えてしまい、CSS / JS / その他 critical resource が後回しになった
- 結果として FCP も伸び、LCP 候補画像自体のダウンロード完了も遅くなった
- 「LCP 候補をブラウザに早く知らせる」最適化は、**画像が軽いことが大前提**

**ルール**:
- preload / fetchpriority="high" は **軽い critical resource** にだけ使う（〜100KB 目安）
- 重い画像（>200KB）への先読みヒントは LCP を悪化させる可能性が高い
- パフォーマンス改善は **「画像本体を軽くする → 先読みヒントを付ける」の順序が必須**
- HTML 属性レベルの変更でも必ず PSI で前後比較してからコミット（UX劣化なし＝スコア改善とは限らない）

**対策**:
- 画像最適化（リサイズ + WebP化 + CDN中継）を **先に** Issue 化して対応
- 軽量化が完了してから fetchpriority / preload を再検討
- PSI で 2 回計測して variance ではないことを確認するルールを徹底
